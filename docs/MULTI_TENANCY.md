# Мультитенантность в FluxCore

FluxCore использует **shared-schema мультитенантность** — все клиенты
живут в одной базе данных, изоляция обеспечивается на уровне прав
доступа и владения объектами, а не отдельными схемами/базами на клиента.

## Почему так, а не отдельная БД на клиента

Для self-hosted продукта, который продаётся как лицензия на
инсталляцию (см. `docs/LICENSING.md`), схема "одна инсталляция = один
клиент" уже даёт физическую изоляцию — у каждого покупателя лицензии
своя копия панели и своя БД. Shared-schema мультитенантность актуальна
**внутри одной инсталляции** — когда владелец панели (реселлер верхнего
уровня) хочет обслуживать множество своих клиентов из одной установки.

## Как устроена изоляция

- **`User.parent_reseller`** — иерархия: обычный клиент привязан к
  реселлеру, который его создал (см. `apps/resellers`).
- **`Client.owner`** — каждый VPN-клиент принадлежит конкретному
  пользователю; реселлер видит только субклиентов, созданных им самим
  (`get_reseller_customers()` в `apps/resellers/services.py`).
- **`ResellerProfile.is_approved`** — реселлер активен только после
  одобрения администратором верхнего уровня — это точка контроля
  верхнего тенанта над нижними.
- **Биллинг и рефералка** также скоуплены через `payment.user` →
  `parent_reseller`/`referrer` — комиссии считаются по этой иерархии.

## Что это НЕ даёт из коробки

- Разные реселлеры **не** могут иметь полностью независимые темы
  оформления на одном инстансе — тема сейчас глобальная
  (`panel_settings.Theme.is_active`). Если нужен per-reseller
  white-label на одной инсталляции — потребуется добавить
  `Theme.reseller` FK и матчинг темы по домену/поддомену реселлера
  (см. `docs/WHITE_LABEL.md` для текущего решения на уровне лицензии).
- Нет ограничения "реселлер A не видит существование реселлера B" на
  уровне админки Django — админка полностью открыта суперпользователям.
  Если нужна многоуровневая изоляция в самой админке — потребуется
  либо `django-tenant-schemas`/`django-tenants` (schema-per-tenant,
  более тяжёлая архитектура), либо кастомные `get_queryset()`
  переопределения во всех ModelAdmin по User.parent_reseller текущего
  админа.

## Рекомендация

Для большинства сценариев продажи (один реселлер верхнего уровня
управляет своими клиентами через API/бота, не имеет доступа в
Django-админку напрямую) текущей схемы достаточно. Полноценный
schema-per-tenant стоит внедрять только если у вас появится сценарий
"продать саму панель как SaaS с self-serve регистрацией конкурирующих
реселлеров, не доверяющих друг другу и админке".
